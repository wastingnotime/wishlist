# Wishlist visitor retention and deletion proposal

Status: **periods accepted by the product owner; API cleanup implemented in the working tree; pending privacy/legal, infra-platform, and deployment review**, 2026-10-02. The owner accepted the proposed moderate periods for this simple vote/suggestion service, shortening the vote window from 24 to **12 months**. These are product decisions, **not statutory LGPD or GDPR periods or an approved published policy**. The code change does not establish production deployment, rights-request handling, or external log/backup controls. Tracks [WNT-87](https://linear.app/wastingnotime/issue/WNT-87/wishlist-enforce-retention-and-cleanup-of-visitor-data) and [WNT-88](https://linear.app/wastingnotime/issue/WNT-88/wishlist-support-verified-access-correction-and-erasure-requests). See the [processing and legal-basis proposal](processing-and-legal-basis.md).

## Current behavior and proposed schedule

Before the API change, expiry denied use of OTP challenges and sessions but did not physically delete their PostgreSQL rows. A successful OTP verification removed that challenge; a new request replaced the challenge for the same email; logout removed only the current session. OTP request rows had a rolling one-hour throttle but no cleanup. Identities, votes, and suggestions had no automatic retention limit. The new API migration adds `last_verified_at`; startup and an hourly worker run transactional cleanup. It removes expired challenges and sessions, request history after the throttle window, overdue private suggestions, votes after 12 months without reverification, and empty identities after the session validity plus 90 days. It logs an aggregate count of pending suggestions older than the 90-day review target. The production runtime must still be promoted and checked. `README.md` says the legacy SQLite source remains untouched after import. The [infra-platform Wishlist stack](https://github.com/wastingnotime/infra-platform/blob/main/terraform/environments/production/swarm-deploy/stacks/wishlist.yml) mounts PostgreSQL at `/volume/wishlist/postgres`, but its checked stack and [runtime decision](https://github.com/wastingnotime/infra-platform/blob/main/work/slices/2026-09-28-wishlist-production-runtime.md) specify no Wishlist backup schedule or restore procedure. A persistent volume is not a backup. The checked stack specifies no per-service log retention. The [shared transactional-email contract](https://github.com/wastingnotime/infra-platform/blob/main/docs/contracts/shared-services/transactional-email-contract.md) records two days of Mailgun Logs on the Free plan as observed on 2026-09-27; the account settings and other provider record classes still need review.

The product-selected periods bound the personal data needed to maintain a current demand signal and review ideas. They are judgment calls for this product, not legal defaults. “Last verification” means the last successful email OTP verification for that identity; migration 003 adds this field and backfills it from identity creation or available sessions. The 12-month vote window means totals can fall when dormant identities expire. Disclose that consequence in the notice.

**Owner direction on log numbers, 2026-10-02:** use **30 days maximum for routine Wishlist application and proxy logs** as the product target. Mailgun Logs were observed at **two days** on the platform's Free plan on 2026-09-27; record that as an observed provider setting, not a WNT-configured retention promise. Stored OTP message bodies, bounce/complaint suppressions, and any other provider records have separate, unverified periods. The checked Wishlist stack has no per-service log-retention setting, so the 30-day target is not yet an enforced production control. Infra-platform must identify the actual log destinations and configure or verify their expiry before the public-voting release decision.

The 24-hour cleanup service level limits how long expired technical records remain in the live store; it does not delay an approved erasure request. The 30-day routine-log and conditional backup targets depend on infra-platform confirmation. Mailgun provider records need class-by-class review because delivery logs, stored message bodies, and suppressions can follow different periods. No permanent retention of identity-linked votes or suggestions is proposed.

## Implementation and rights semantics to approve

1. Use a scheduled cleanup independent of incoming OTP traffic; make it idempotent and safe under concurrent verification and voting. Measure deleted rows without logging emails or tokens.
2. On approved erasure, verify the requester, revoke every session, remove the email/identity and linked vote and private suggestion data in a transaction, and update vote counts without changing feature lifecycle. Re-registration with the same email should create a fresh identity unless an approved exception explicitly requires a minimal record.
3. Define whether accepted public feature text must be edited or removed when a request concerns content the visitor supplied. Inspect it for personal data rather than assuming it is anonymous.
4. A lawful retention exception needs a named purpose, affected fields, access restriction, owner, and expiration date. Rights requests require a private intake and response channel; a public issue is not suitable.
5. Reconcile deletion against backups, restored databases, legacy SQLite, provider logs, and any export. Do not claim completed erasure while a restore can silently reintroduce the record.

## Approval blockers

- Product/privacy owner: periods accepted on 2026-10-02, including that vote totals decrease after **12 months** without renewed verification. Confirm the notice clearly describes this behavior.
- Legal reviewer: confirm permitted retention exceptions, erasure/correction handling, and notice wording under LGPD; assess GDPR applicability and any additional requirements.
- Infra-platform and provider owners: confirm whether the 30-day routine-log and conditional backup limits are achievable, plus backup locations, processor terms, and restoration procedure. The minimum backup/restore implementation and drill are tracked as [WNT-102](https://linear.app/wastingnotime/issue/WNT-102/wishlist-establish-and-test-postgresql-backup-and-restore-before) before public voting; later disaster recovery refinements may follow separately.
- Wishlist implementation owner: implement and verify cleanup and rights workflows before public voting; then record actual behavior in the notice and production readiness decision.
